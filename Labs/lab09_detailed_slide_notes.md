## Слайд 3. Git hooks полезны, но нужны проверки на сервере

**Время:** 02:00–04:00.  
**Формат:** основная мотивация CI.

### Как работают наши Git hooks

```text
git commit
    ↓
pre-commit → prek → chk
    ↓
commit-msg → prek → convco
    ↓
коммит создан
```

Git hook — программа, которую Git вызывает при определённом событии. У нас `pre-commit` проверяет качество кода до коммита, а `commit-msg` — сообщение коммита.

В новом клоне хуки можно установить командой:

```bash
prek install --hook-type pre-commit --hook-type commit-msg
```

Либо, если в `.pre-commit-config.yaml` прописаны `default_install_hook_types`, достаточно `prek install`.

### Почему одних локальных хуков недостаточно

**Ситуация 1. Хуки не установлены.** После `git clone` содержимое `.git/hooks/` не переносится из исходного репозитория как рабочие хуки.

**Ситуация 2. Хуки можно обойти или изменить.** Локальная конфигурация контролируется разработчиком; нельзя полагаться на то, что каждый коммит обязательно прошёл проверки.

**Ситуация 3. Среды отличаются.** Код, проходящий тест на одном компьютере, может не сработать на другом из-за локальных библиотек, версий инструментов или неявной конфигурации.

### Что даёт CI

```text
git push / pull request
    ↓
GitHub получает изменение
    ↓
Запускает runner
    ↓
Скачивает код
    ↓
Устанавливает окружение
    ↓
Выполняет проверки
    ↓
SUCCESS / FAILURE
```

**Runner** — машина, выполняющая задания GitHub Actions. В нашем случае это виртуальная машина GitHub с Ubuntu.

**Главное отличие:** Git hooks выполняются локально, а CI — независимо после отправки изменений. Результат виден в интерфейсе GitHub.

**Технический нюанс:** красный CI сам по себе ещё не запрещает слияние Pull Request. Если хотим блокировать merge при ошибках, нужно настроить branch protection/rulesets и required status checks. Это отдельная тема.

Открыть репозиторий на GitHub и вкладку **Actions**. Если уже есть история запусков, показать зелёный и красный значки. Сразу открыть `.github/workflows/ci.yml`.

## Слайд 4. Workflow: инструкции для GitHub

**Время:** 04:00–06:00.  
**Формат:** разбор YAML на экране.

### Основные понятия

**Workflow** — автоматизированный процесс, описанный в YAML-файле внутри `.github/workflows/`.

**Job** — задание, исполняющееся на runner. В одном workflow может быть несколько jobs.

**Step** — шаг внутри job. Шаги одного job выполняются последовательно, если конфигурация не задаёт иного поведения.

```text
Workflow: CI
└── Job: checks (Ubuntu runner)
    ├── Step: checkout репозитория
    ├── Step: установка Nix
    ├── Step: конфигурация Cachix
    ├── Step: установка devenv
    ├── Step: chk
    └── Step: cargo test
```

### Показываем файл `.github/workflows/ci.yml`

```yaml
name: CI

on:
  push:
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  checks:
    name: Quality and tests
    runs-on: ubuntu-24.04
    env:
      SQLX_OFFLINE: "true"

    steps:
      - name: Checkout repository
        uses: actions/checkout@v7
        with:
          persist-credentials: false

      - name: Install Nix
        uses: cachix/install-nix-action@v31

      - name: Configure devenv binary cache
        uses: cachix/cachix-action@v16
        with:
          name: devenv

      - name: Install devenv
        run: nix profile add nixpkgs#devenv

      - name: Check formatting and static analysis
        run: devenv shell -- chk

      - name: Run Rust unit tests
        run: devenv shell -- cargo test --locked
```

### Разбираем ключи

- `name: CI` — отображаемое имя workflow.
- `on` — события запуска: `push`, события `pull_request` и ручной `workflow_dispatch`.
- `jobs` — набор заданий.
- `checks` — внутренний идентификатор нашего job.
- `runs-on: ubuntu-24.04` — выбор стандартной среды исполнения GitHub.
- `steps` — последовательные шаги задания.
- `uses` — использование готового Action (например, `actions/checkout`).
- `run` — shell-команда.
- `permissions: contents: read` — минимально необходимые права токена.
- `persist-credentials: false` — не сохранять учётные данные checkout для последующих команд.

**Полезная деталь:** отправка Git-тега тоже является событием `push` и запустит этот workflow, поскольку фильтрации веток и тегов нет.

### Главная идея слайда

```yaml
- name: Check formatting and static analysis
  run: devenv shell -- chk
```

Мы **не переписываем** правила форматирования и линтинга в GitHub Actions. Вызываем уже созданную команду `chk` из `devenv` (она использует `scripts/quality.sh`). Один источник правил — для локальной работы и CI.

**Что показать:** идти по YAML сверху вниз. Не тратить время на все параметры Actions; важно усвоить иерархию **workflow → job → steps**.

## Слайд 5. Одна среда локально и на CI

**Время:** 06:00–08:00.  
**Формат:** разбор запуска на runner.

### Последовательность после `git push`

1. GitHub выделяет виртуальную машину **Ubuntu 24.04**.
2. `actions/checkout` загружает репозиторий, в том числе `Cargo.toml`, `Cargo.lock`, `devenv.nix` и `devenv.lock`.
3. Устанавливается **Nix**.
4. Подключается бинарный кеш **Cachix** для снижения затрат на повторные сборки Nix-зависимостей.
5. Устанавливается **devenv**, затем через него выполняются проверки и тесты.

### Почему команды выглядят по-разному

На компьютере разработчика, когда direnv уже активировал devenv:

```bash
chk
cargo test --locked
```

На GitHub runner:

```bash
devenv shell -- chk
devenv shell -- cargo test --locked
```

`devenv shell -- <команда>` выполняет команду в окружении проекта. CI не зависит от пользовательского интерактивного shell и настройки direnv.

### Что такое Cachix

Nix может собирать зависимости из исходников, но это долго. **Binary cache** — хранилище уже собранных результатов, которое позволяет не собирать одно и то же повторно.

Здесь важно не перепутать его с кешем компиляции Rust `target/`: это разные уровни кеширования.

### Почему сейчас Ubuntu, а позже Debian

Фраза преподавателя:

«Сегодня GitHub выделяет нам стандартный Ubuntu runner. С помощью Nix/devenv мы используем декларативно описанное окружение. Позже для production выберем Debian, подготовим серверную/контейнерную сборку и адаптируем CI, чтобы она проверялась в Debian-окружении».

**Нюанс:** стандартного GitHub-hosted runner с `runs-on: debian` нет. Debian можно получить через job/container на Ubuntu или с помощью своего runner. Однако установка Nix внутри контейнера может потребовать дополнительной настройки; сегодня этого не касаемся.

### Что показать

В готовом запуске открыть список шагов. Можно показать, что `chk` и тесты реально выполнялись на GitHub. Если сборка занимает долго, не ждать её окончания перед аудиторией.

## Слайд 6. SQLx Offline: компиляция без PostgreSQL

**Время:** 08:00–09:30.  
**Формат:** объяснение + короткая демонстрация.

### Вспоминаем SQLx

Пример запроса:

```rust
let row = sqlx::query!(
    "SELECT prediction FROM predictions WHERE id = $1",
    id
);
```

Макрос `query!` проверяет SQL на этапе компиляции. В обычном режиме для этого нужна база с актуальной схемой: SQLx узнаёт названия и типы столбцов, параметры и форму возвращаемых данных.

### Проблема в CI

На новой машине PostgreSQL ещё не запущен. Для простого lint/test job нам не обязательно поднимать БД только ради compile-time проверки SQL-запросов.

### Подготовка метаданных локально

**Перед этим:** PostgreSQL запущена, миграции применены, `DATABASE_URL` указывает на нужную учебную базу.

```bash
cargo sqlx prepare -- --all-targets
```

Если запросы скрыты за feature flags, может потребоваться подготовка с `--all-features` (подбираем флаги под конкретный проект).

Команда создаёт файлы вида:

```text
.sqlx/
├── query-<hash>.json
├── query-<hash>.json
└── ...
```

Там находятся метаданные SQL-запросов, необходимые для их проверки в offline-режиме. Эти файлы **можно и нужно коммитить**, так как они описывают запросы, а не содержат пароль базы.

```bash
git add .sqlx/
git commit -m "build: prepare SQLx offline metadata"
```

### Как это используется в CI

```yaml
env:
  SQLX_OFFLINE: "true"
```

SQLx берёт сведения из `.sqlx/` вместо подключения к живой базе во время компиляции. Важно: это помогает **компилировать код**, но не позволяет реально выполнять обращения к PostgreSQL без PostgreSQL.

Если изменились миграции или SQL-запросы, нужно обновить offline-метаданные. Команда `cargo sqlx prepare --check` позволяет проверить их актуальность при наличии доступной базы с применёнными миграциями.

### Что показать

1. Открыть один файл `.sqlx/query-….json`.
2. Найти в нём SQL-запрос и сведения о типах.
3. Вернуться к `SQLX_OFFLINE: "true"` в workflow.

**Переход:** «Теперь компиляция не требует БД. А что именно будет проверять тест?»

## Слайд 7. Один unit-тест: проверяем правило

**Время:** 09:30–10:30.  
**Формат:** небольшой пример и запуск.

### Что такое автоматический тест

Тест — программа, проверяющая, что поведение соответствует ожидаемому. Для Fortune Pies можно проверить правило: предсказание не должно быть пустым или состоять только из пробелов.

Если в реальном приложении уже есть подходящая чистая функция, лучше тестировать её. Пример ниже — демонстрационный.

```rust
pub fn is_valid_prediction(s: &str) -> bool {
    !s.trim().is_empty()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn rejects_blank_prediction() {
        assert!(!is_valid_prediction("   "));
        assert!(is_valid_prediction("Удача рядом"));
    }
}
```

### Что объяснить в Rust

- `#[cfg(test)]` — модуль включается в тестовую конфигурацию сборки.
- `#[test]` — помечает функцию как тест.
- `assert!` — проверяет логическое условие; если оно ложно, тест падает.
- `trim()` — убирает пробельные символы по краям строки.
- `!` — логическое отрицание.

### Команда

```bash
cargo test --locked
```

Пример результата:

```text
running 1 test
test tests::rejects_blank_prediction ... ok

test result: ok. 1 passed; 0 failed
```

### Что означает `--locked`

Cargo требует, чтобы существующий `Cargo.lock` соответствовал `Cargo.toml`, и **не изменяет lockfile**. Если lockfile отсутствует или нуждается в обновлении, команда завершается ошибкой.

В CI это полезно: GitHub не должен незаметно менять граф зависимостей, забытый разработчиком.

### Unit-тест против интеграционного

- **Unit-тест:** проверяет отдельную функцию/правило, может работать без БД.
- **Интеграционный тест:** проверяет взаимодействие компонентов, например HTTP API + PostgreSQL; требует соответствующего окружения.

Сегодня выбираем unit-тест. Интеграционные тесты сделаем позднее.

**Что показать:** один успешный `cargo test --locked`. На следующем слайде сознательно изменим ожидаемый результат теста.

## Слайд 8. Демонстрация: зелёный → красный → зелёный

**Время:** 10:30–15:30.  
**Формат:** главная практическая часть.

> **Подготовить заранее:** хотя бы один успешный и один неуспешный запуск в истории Actions. Установка Nix и первая компиляция Rust могут длиться дольше, чем вся демонстрация.

### Этап 1. Успешный запуск

Открываем **GitHub → Actions → CI → успешный run → Quality and tests**.

Ожидаем увидеть последовательность зелёных шагов:

```text
✓ Checkout repository
✓ Install Nix
✓ Configure devenv binary cache
✓ Install devenv
✓ Check formatting and static analysis
✓ Run Rust unit tests
```

**Объяснить:** в Unix команда обычно возвращает код `0` при успехе и ненулевой код при ошибке. GitHub Actions оценивает результат шага по завершению команды.

### Этап 2. Создаём демонстрационную ветку

```bash
git switch main
git pull --ff-only
git switch -c lab09/demo
```

**Намеренно меняем ожидание теста**, не ломая синтаксис:

Было:

```rust
assert!(!is_valid_prediction("   "));
```

Стало:

```rust
assert!(is_valid_prediction("   "));
```

Теперь тест ошибочно ожидает, что строка из пробелов допустима, хотя функция возвращает `false`.

Это полезная демонстрация: код компилируется и может пройти форматтер/линтер, но тест показывает неправильное ожидание.

### Этап 3. Отправляем ошибочный коммит

```bash
# Здесь тест для примера лежит в src/lib.rs.
# Если выбрано другое место — исправить путь.
git add src/lib.rs
git commit -m "test: demonstrate a failing CI run"
git push -u origin lab09/demo
```

**Важный момент:** `chk` в нашей конфигурации не запускает этот тест, поэтому локальные хуки не обязаны поймать такую ошибку. Отдельный шаг `cargo test` в CI её найдёт.

### Этап 4. Читаем красный лог

На GitHub открываем запуск для ветки `lab09/demo`.

Ожидаемо:

```text
✓ Check formatting and static analysis
✗ Run Rust unit tests
```

Фрагмент лога будет примерно таким:

```text
test tests::rejects_blank_prediction ... FAILED

assertion failed: is_valid_prediction("   ")

test result: FAILED. 0 passed; 1 failed
error: test failed
```

**Что объяснить:** GitHub не знает, что правильное предсказание должно содержать текст. Это правило формализовали **мы** в тесте. Когда `assert!` получает ложное условие, тест завершается ошибкой, `cargo test` возвращает ненулевой код, а CI помечает шаг как неуспешный.

### Этап 5. Исправляем и отправляем повторно

Возвращаем:

```rust
assert!(!is_valid_prediction("   "));
```

```bash
git add src/lib.rs
git commit -m "test: restore correct expectation"
git push
```

Открываем следующий run: `Quality and tests` снова зелёный.

**Финальная реплика слайда:** «Теперь каждая отправка изменений независимо проверяется на другой машине. И любой участник команды видит, прошёл код проверки или нет».

**Не делаем:** не сливаем намеренно сломанный коммит в `main`. Если в аудитории CI запускается слишком долго, показываем заранее подготовленные запуски.

## Слайд 9. Фиксируем первую учебную версию

**Время:** 15:30–18:00.  
**Формат:** объяснение Git-тегов + команды.

### Что такое Git-тег

Коммиты идентифицируются хешами, но их неудобно использовать как человекочитаемые версии. Тег даёт понятное имя конкретному состоянию репозитория.

```text
main
 │
 A ── B ── C ── D
                ↑
             v0.1.0
```

После новых коммитов ветка `main` пойдёт дальше, а опубликованный релизный тег обычно оставляют на том же коммите:

```text
main
 │
 A ── B ── C ── D ── E ── F
                ↑         ↑
             v0.1.0     HEAD
```

Технически теги можно переписывать, но опубликованные релизные теги обычно считают неизменяемыми.

### Семантическое версионирование

`MAJOR.MINOR.PATCH`:

- `MAJOR` — несовместимые изменения публичного API;
- `MINOR` — новая обратно совместимая функциональность;
- `PATCH` — обратно совместимые исправления.

`0.1.0` — ранняя стадия; для нашего занятия это **условная первая учебная версия**. Не нужно доказывать production-готовность.

### Действия

```bash
git switch main
git pull --ff-only
```

Проверяем, что последний коммит `main` прошёл CI, затем:

```bash
git tag -a v0.1.0 -m "Fortune Pies 2026"
git push origin v0.1.0
git show v0.1.0 --no-patch
```

- `git tag -a` создаёт **аннотированный тег** с собственными метаданными.
- `-m` задаёт сообщение аннотированного тега.
- `git push origin v0.1.0` публикует тег на GitHub.
- `git show v0.1.0 --no-patch` показывает сведения о теге и коммите без diff.

**Отличие от GitHub Release:** Git-тег — объект Git. GitHub Release — дополнительная публикация версии с описанием, файлами и, возможно, бинарными артефактами. Мы создаём тег, но **не собираем Docker-образ и не деплоим приложение**.

**Нюанс:** поскольку `on: push:` не ограничен ветками, отправка тега может вызвать ещё один запуск CI. Тег следует ставить после подтверждённого успешного CI соответствующего коммита.

## Слайд 10. Что дальше — уже в следующем году

**Время:** 18:00–20:00.  
**Формат:** завершение и анонс следующих тем.

### 1. Debian для production

«Пока мы разрабатывали и проверяли приложение. Но настоящий сервис должен постоянно работать на сервере. Позже выберем Debian для production, подготовим сборку, конфигурацию и развёртывание, а CI адаптируем под Debian-окружение».

В рамках будущих занятий:

- серверное окружение Debian;
- Docker, Dockerfile и при необходимости Docker Compose;
- HTTPS/TLS, reverse proxy;
- запуск сервиса, управление настройками и секретами;
- миграции при развёртывании;
- проверки в Debian-контейнере или на Debian runner.

### 2. Надёжность и наблюдаемость

- интеграционные тесты с PostgreSQL;
- логирование через `tracing`;
- диагностика ошибок и эксплуатационные практики;
- проверка актуальности `.sqlx/` относительно настоящей схемы БД.

**Разница CI и CD:** CI — интеграция и проверка изменений. Continuous Delivery готовит проверенную версию к поставке; Continuous Deployment автоматически развёртывает её. Сегодня у нас **CI, а не CD**.

### 3. Git worktree вместе с Codex

«Когда будем подходить к работе с AI-агентами, изучим `git worktree`: несколько рабочих каталогов одного репозитория для разных веток. Это удобно для параллельной разработки и для выделения отдельного дерева под задачи Codex».

Сегодня worktree только анонсируем — **не демонстрируем**.

### Финальные слова

«Мы начали с небольшого Rust-сервера, научились подключать PostgreSQL, управлять миграциями, воспроизводить окружение, проверять код и безопасно хранить секреты.

Сегодня добавили CI — теперь проект может независимо проверять себя после отправки изменений.

Мы зафиксировали `v0.1.0`. Это ещё не production, но уже законченный этап разработки. В следующем году будем двигаться от локального приложения к серверному развёртыванию».
